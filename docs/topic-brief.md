# 題材企画: ThreadLocalの残留で別テナントの監査ログが混ざる

## 対象

| 項目 | 内容 |
| --- | --- |
| 対象言語 | Java 21 |
| 対象読者 | Javaの基本文法と`ExecutorService`を使うバックエンド開発者 |
| 難易度プロファイル | 実践・上級 |
| 選定理由 | 単独タスクでは正常に見える一方、ワーカースレッドの再利用と暗黙コンテキストの残留が組み合わさるため、ログ・テスト・デバッガーでの切り分けが必要になるためです。 |
| 実行基盤 | JDK 21の`javac`と独自の最小テストランナー。外部依存はありません。 |
| フレームワーク非依存性 | Spring、MDC、サーブレットを使用せず、`ThreadLocal`と`Executors.newSingleThreadExecutor()`だけで同じ失敗を再現します。 |

## 学習する契約

> テナント`tenant-a`のジョブを処理した同一ワーカーでテナント未指定のシステムジョブを続けて実行しても、後者の監査イベントの帰属先は`SYSTEM`であるべきですが、バグ状態では`tenant-a`になります。

### 対象の直接原因

テナント処理が`ThreadLocal`へ値を設定した後、ワーカースレッドをプールへ返す前に`remove()`を呼ばないことです。単一ワーカー実行器が同じスレッドを順に使うため、次の未スコープジョブが前タスクの値を読みます。

### 対象外

Springのリクエストスコープ、SLF4J MDC、非同期境界でのコンテキスト伝播、仮想スレッド、メモリリーク一般、テナント認可の実装は対象外です。

## 再現設計

| 要素 | 決定 |
| --- | --- |
| 公開境界 | `AuditJobRunner.runTenantExport`および`AuditJobRunner.runSystemReconciliation` |
| 入力・初期状態 | `tenant-a`のエクスポートを先に実行し、同じ`AuditJobRunner`上でテナント未指定の照合ジョブを実行します。 |
| Redの観測 | 未スコープジョブの戻り値と監査台帳の最終イベントが`SYSTEM`ではなく`tenant-a`となるアサーション差分です。 |
| 最終観測 | 戻り値に加え、`AuditLedger`へ保存された2件目の監査イベントを独立して確認します。 |
| 決定性 | `newSingleThreadExecutor()`と各`Future.get()`による完了待機で、同じワーカー上の順序を固定します。`sleep`は使いません。 |
| 固定状態の検証コマンド | `./scripts/test.sh` |
| バグ状態の確認コマンド | `./scripts/test.sh` |

## 仮説

| 仮説 | どう検証または除外するか |
| --- | --- |
| テナント未指定時の既定値が誤っている | 新しい`AuditJobRunner`で未スコープジョブだけを実行し、`SYSTEM`となることを確認します。 |
| テナントIDが共有台帳で上書きされている | 戻り値と台帳を分けて確認し、どちらも同じワーカー上で誤帰属することを確認します。 |
| 前ジョブの`ThreadLocal`値が残っている | 診断出力とデバッガーで、2件目のタスク開始時点のコンテキストが`tenant-a`であることを確認します。 |

## 予定する履歴

| 順序 | コミットの目的 | 期待する状態 |
| --- | --- | --- |
| 1 | 単一ワーカーでの監査ジョブを再現する | 対象テストが`SYSTEM`と`tenant-a`のアサーション差分で失敗します。 |
| 2 | テナントコンテキストをタスク境界で解放する | 同じテストと全テストが成功します。 |
